## Context

See `proposal.md` - Why for the motivation. Relevant current state:

- `backend/src/services/ramp/bridge.ts` already isolates all hardware interaction behind two MQTT topics (`ramp/{vehicle_id}/cmd`, `ramp/{vehicle_id}/state`) with a small JSON contract — the wire boundary this change targets already exists and does not need to change.
- `backend` compiles to a single self-contained binary (`bun build --compile`) and deploys as one container; `frontend` builds to a single static export (`output: 'export'`, no server at runtime).
- `fleet`'s `apps/rampme/` currently has exactly one namespace, one backend `Deployment`, and no notion of a non-production environment anywhere in the reconcile graph. Public hostnames are wired through OpenTofu (`tofu/tunnel.tf`, `tofu/dns.tf`), applied by hand, outside Flux's reconcile loop.
- The backend CI workflow already tags every `main` build as `stage-<timestamp>` in GHCR; nothing consumes that tag today.

## Goals / Non-Goals

**Goals:**
- Make the ramp reservation-to-deploy lifecycle, including failure and timeout paths, exercisable end to end without physical hardware, a second managed broker, or touching production.
- Give "staging" an actual isolated backend to mean something, for both manual verification and (later) automated e2e.
- Make the frontend's environment selection self-contained and safe-by-default, so an unrecognized deployment context cannot reach production.

**Non-Goals:**
- Firmware conformance testing for `rampme-hardware`. The simulator is `rampme-software`'s own approximation of hardware behavior for its own testing purposes, not a certification suite; the wiki protocol page remains the cross-repo contract, and `rampme-hardware` gains no code dependency on this repo.
- Unit/integration test coverage of the reservation state machine itself (issue #36). That is testable directly against `db/ramp.ts` and `bridge.ts` without any deployed simulator, and is tracked separately.
- Ephemeral, per-PR stage environments. Stage is one permanent, versioned deployment with its own lifecycle.
- Implementing the `fleet`-side manifests or the OpenTofu changes. This design specifies exactly what they need to be; applying them is a separate PR in that repository.

## Decisions

**New app is named `hw-sim/`.** Short, consistent with the existing lowercase, unhyphenated-where-possible `backend/`/`frontend/` naming, and unambiguous as a sibling in the repo root. Alternative considered: nesting it under `backend/` behind a `MOCK_RAMP`-style conditional — rejected (per exploration) because it would branch the single-binary `bun build --compile` output and blur the top-level app boundary the rest of the repo's tooling (per-app `AGENTS.md`, per-app CI workflow) assumes.

**hw-sim embeds its own MQTT broker in-process rather than using a second managed broker or a separate broker container.** A pure-JS/TS broker library running over `node:net` (Bun supports this) lets one small process be both the transport and the simulated hardware, with the simulator able to react to published commands and publish responses without a network hop to itself. Alternative considered: a standalone broker (e.g. Mosquitto) plus a separate simulator client — rejected because it adds a second piece of infrastructure to operate for no behavioral benefit, and the project explicitly does not want a second managed broker running anywhere, even for tests.

**Behavior profile switching is an HTTP control endpoint on hw-sim** (e.g. `POST /vehicles/:vehicleId/profile`), not an environment variable fixed at boot or an MQTT control topic. An env-var-only approach can't change behavior mid-run without a pod restart, which is unworkable for a scripted e2e suite that wants both a happy-path and a timeout scenario in the same run. An MQTT control topic keeps everything on one transport but forces every caller (tests, manual scripts) to speak MQTT instead of a plain HTTP call. The HTTP endpoint is a small, additive surface (on the order of tens of lines) that doesn't touch the ramp MQTT protocol itself.

**hw-sim duplicates the protocol's action/state constants rather than importing them from `backend` or sharing a package with `rampme-hardware`.** The protocol is small and stable, and is already the wiki's job to document for cross-repo consumers. Taking a code dependency from `rampme-hardware` on `rampme-software` (or vice versa) would couple two repositories that are deliberately independent; duplicating a handful of string literals is cheaper than that coupling.

**hw-sim ships as its own `Deployment` + `ClusterIP` `Service` in `fleet`, not a sidecar in the backend-stage pod.** A separate Service means the same image can also be run standalone (local dev, a future CI e2e job) without depending on how `backend-stage`'s pod is shaped, at the cost of one more `Deployment`/`Service` pair in `fleet` (no `PersistentVolumeClaim`, no `Secret`, no `HTTPRoute` — it holds no state and is never reachable outside the cluster).

**`backend-stage` is a full peer of the production backend `Deployment` in `fleet`, not a flag on it.** Restructure `apps/rampme/backend/` into a Kustomize `base/` (the `Deployment` shape shared by both environments: replicas, strategy, container port, volume mount, probes — no image tag, no MQTT env, no PVC claim name baked in) plus `overlays/production/` and `overlays/stage/`, each supplying its own identity (name, labels/selector, image + `$imagepolicy` marker, `PersistentVolumeClaim`, `ImageRepository`/`ImagePolicy`, `HTTPRoute`) and MQTT wiring (`overlays/production` keeps the existing `secretRef`; `overlays/stage` sets a plain `MQTT_URL` env var pointed at hw-sim's in-cluster DNS name, since hw-sim accepts unauthenticated connections and needs no `secret.yaml`). `overlays/stage`'s `ImagePolicy` filters `^stage-(?P<ts>[0-9]+)$`, extracts the numeric timestamp (`extract: '$ts'`), and selects ascending (`policy.numerical.order: asc`) so the highest (most recent) timestamp always wins — the same shape `overlays/production`'s `ImagePolicy` already uses for its `prod-<ts>` tags, and the pattern `hw-sim`'s own `ImagePolicy` mirrors for its `stage-<ts>` tags. `filterTags.pattern` only selects which tags are eligible; ordering is `policy.numerical`'s job.
Renaming an object (`rampme-backend` -> `rampme-backend-stage`) has to go through a JSON6902 `replace` on `/metadata/name` in each overlay's patch, not a strategic-merge patch — strategic merge treats `metadata.name` as the match key, not a mergeable field, so it silently leaves the original name in place. Kustomize's built-in `nameReference` transformer (used by `nameSuffix`) also does not know about Gateway API's `HTTPRoute.spec.rules[].backendRefs[].name`, so an auto-suffix approach left `overlays/stage`'s `HTTPRoute` pointing at the production `Service` — verified by rendering with `kubectl kustomize` and inspecting the output, not assumed. Every identity field (name, labels, selector, `backendRefs`, PVC `claimName`) is therefore set explicitly per overlay rather than derived through a transformer. `overlays/production` renders byte-identical to today's live manifests (diffed via `kubectl kustomize` against the pre-restructure files), so the restructure itself is a no-op for the running production `Deployment`/`Service`/`PersistentVolumeClaim`. The existing single `apps/rampme/imageupdateautomation.yaml` (scoped to `./apps/rampme`, `strategy: Setters`) needs no change: it text-scans every YAML file under that path for the marker comment regardless of Kustomize structure, so it finds the marker inside an overlay's patch file the same way it found it inline in the old flat `deployment.yaml`.

**`backend-stage` gets a real public hostname** (proposed: `api-stage.rampme.site`, matching the `api.` naming already used for production), reachable the same way production is: a second named listener on the shared Envoy Gateway (`infrastructure/configs/envoy-gateway/gateway.yaml` currently has exactly one listener, `rampme-api`, hardcoded to `api.rampme.site` — add `rampme-api-stage` for the new hostname), a new `HTTPRoute` referencing that `sectionName`, a new ingress rule appended to the existing `cloudflare_zero_trust_tunnel_cloudflared_config` resource in `tofu/tunnel.tf` (the same tunnel; that file's own comment warns that *replacing* the tunnel resource takes production down, so this must land as an in-place update to the `ingress` list, confirmed via `tofu plan` before apply, not asserted here), and a new `cloudflare_dns_record` in `tofu/dns.tf`. Applied by hand, per `fleet`'s existing OpenTofu convention — not a reason to skip public exposure, since the frontend's staging preview needs a real HTTPS origin to call.

**Frontend API resolution moves from a single build-time-baked `NEXT_PUBLIC_API_URL` to a hostname lookup table in `frontend/lib/config.ts`, evaluated at runtime in the browser**, in this order: (1) an explicitly-set `NEXT_PUBLIC_API_URL` at build time still wins outright; (2) `process.env.NODE_ENV === 'development'` (i.e. `next dev`) falls back to `/api`, preserving local dev's existing `next.config.ts` rewrite-proxy path unchanged and independent of the hostname table below; (3) `window.location.hostname === 'rampme.site'` → production API; (4) `window.location.hostname === 'staging.rampme.pages.dev'` → stage API; (5) anything else → stage API. Step (5) is a deliberate fail-safe: this backend can send a `deploy` command to physical hardware on a real bus, so an unrecognized origin (an unexpected preview, a locally-served static export, a future domain not yet added to the table) must default away from production, not toward it. Alternative considered: write a small `config.json` into the Pages deploy output right before each `wrangler pages deploy` step, fetched once at runtime — rejected because it needs an extra CI step that can silently drift or be forgotten, adds a network round-trip before the first API call, and only approximates "one artifact" (the JS is identical, but a file next to it differs); the hostname table ships as reviewed, type-checked code and produces a genuinely byte-identical build for every environment. Leave a code comment in `lib/config.ts` pointing at the CORS origin allowlist in `backend/src/index.ts`: both express the same trust boundary from opposite ends, and should be updated together even though nothing enforces that automatically. `.github/workflows/frontend.yaml`'s `deploy-staging` job no longer sets `NEXT_PUBLIC_API_URL` at all, so the one build artifact it produces is the same one deployed to both staging and production — the runtime hostname check is what tells them apart.

**`MOCK_RAMP` is removed, not fixed.** `hw-sim` + `backend-stage` supersede what it was documented to do; leaving a second, still-fake toggle around after building the real thing would reintroduce the exact stale-docs problem this change exists to close.

## Risks / Trade-offs

- **[Risk]** hw-sim's behavior is an approximation of real firmware, not firmware itself — a bug specific to actual hardware timing or MQTT client behavior won't surface here. **Mitigation**: this is explicitly a Non-Goal (see above); real-hardware validation stays the job of `rampme-hardware` and issue #46 (pilot a real ramp on a vehicle), not this change.
- **[Risk]** Adding an ingress rule to the live `tofu/tunnel.tf` resource is a hand-applied change to production-adjacent infrastructure. **Mitigation**: `tofu plan` must be reviewed before apply to confirm it's an in-place update to the `ingress` list, not a resource replacement (the file's own existing comment already warns a replacement takes `api.rampme.site` down); do this as its own isolated `tofu apply`, not bundled with unrelated infra changes.
- **[Risk]** hw-sim being reachable only in-cluster means a developer cannot poke it directly from a laptop without `kubectl port-forward` or going through `backend-stage`. **Mitigation**: acceptable given it's a backend-internal implementation detail, not a user-facing surface; its HTTP control endpoint is meant to be driven by CI/e2e tooling that already runs with cluster access, not by hand from an arbitrary machine.
- **[Trade-off]** Hostname-based frontend resolution couples `lib/config.ts` to specific infrastructure hostnames that used to live purely in CI env vars. A future hostname change is now a frontend PR, not just a CI tweak. Accepted: these hostnames change rarely, and the alternative (external config file) was already rejected above for other reasons.

## Migration Plan

- `rampme-software` changes (new `hw-sim/` app, its CI workflow, `lib/config.ts`'s hostname table, `MOCK_RAMP` removal) are purely additive or dead-code removal — rollback is a plain `git revert`, no data migration, no feature flag needed.
- **BREAKING**: removing `MOCK_RAMP` means anyone currently setting that env var locally sees no behavior change (it already does nothing), but the documentation referencing it disappears; call this out in the PR description so it isn't mistaken for a regression.
- `fleet` changes (new `backend-stage` and `hw-sim` Kustomize resources, new Envoy Gateway listener, new `HTTPRoute`) are additive Kubernetes manifests — rollback is reverting the commit in `fleet` and letting Flux reconcile back, no impact on the production `Deployment`.
- The `tofu/tunnel.tf` and `tofu/dns.tf` changes need their own rollback path: reverting the OpenTofu source and running `tofu apply` again. Because this touches the same tunnel resource production's DNS depends on, treat the initial apply and any rollback apply as deliberate, reviewed, one-at-a-time operations, not bundled with other infra work.
- Sequencing: `hw-sim` and `backend-stage` (fleet) can land and be verified entirely before the frontend hostname change ships, since until then the frontend still resolves via the old build-time `NEXT_PUBLIC_API_URL` bake. The frontend change should land only after `api-stage.rampme.site` is confirmed reachable, so there's no window where "staging" resolves to a hostname that doesn't yet answer.

## Open Questions

- Do PR preview deployments (`<branch>.rampme.pages.dev`) actually exist today? `frontend.yaml`'s `pull_request` trigger only runs `build` and `e2e` — there is no `deploy` job for pull requests, even though `index.ts`'s CORS origin list already allowlists the pattern. If they're produced by a separate mechanism (e.g., Cloudflare Pages' own native Git integration, outside this GitHub Actions workflow), the hostname table's "unrecognized → stage" fallback already covers them with no extra work; if they don't exist at all yet, that CORS entry may be provisioning for a feature that was never finished. Doesn't change this change's approach or specs either way — worth resolving separately.
